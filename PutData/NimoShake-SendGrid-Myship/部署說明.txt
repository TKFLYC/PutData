==========================================================

本包為 賣貨便 (MyShip) 專用，不含任何金鑰。
發信人固定 c2cteam@pic.net.tw，收件人於 conf 設定。

本版更新 (v4.2)
-------------
- 新增「FullCheck 結束通知」: 在 conf 加一行 FULLCHECK_DIR (nimo-full-check.linux 的執行目錄) 後，
  nimo-full-check 全量複核照原本指令跑完 (輸出資料夾出現 run-manifest.json) 1 分鐘內自動寄結果信:
  🟢 PASS / 🟠 PASS_WITH_EXCEPTIONS / 🔴 FAIL + 各 table 統計 (checked/passed/failed/exceptions) +
  異常欄位 Top 5 + 耗時。同一次結果只通知一次 (重跑後舊輸出資料夾被改名加時間戳也不會誤寄)；
  首次啟用只建基準、不補寄歷史結果。範例見 myship.conf.example 的 FULLCHECK_DIR 區塊。
- FullCheck 失敗也會通知: 同時追蹤 fullcheck 程序，程序消失卻沒有新結果檔
  (OOM/kill/連線中斷/磁碟滿) → 寄 🔴「FullCheck 異常結束」告警，附排查步驟；
  判斷前保留約 1 分鐘寬限，避免程序剛結束、結果檔還在寫的誤報。
- 新增「看門狗」(nimoshake-watchdog.sh): 監控「告警引擎本身」——引擎每輪跑完寫心跳，
  看門狗每 5 分鐘獨立檢查，心跳停更 5 分鐘即寄 🔴「監控引擎停擺 (告警失效中)」、
  恢復寄 🟢。看門狗完全不共用引擎程式碼，引擎壞掉仍能寄信。
  排程行已加入 crontab.example，照步驟 3 貼入即自動生效。
- 原生版 fullcheck (不寫 run-manifest.json 的 git 版) 也支援: conf 設
  FULLCHECK_MODE="native"、FULLCHECK_DIR 直接填 -d 輸出資料夾本身，
  並建議設 FULLCHECK_NATIVE_LOG=<啟動時導出的log檔> 以區分跑完/中途掛掉。
  原生版信件為「未發現差異 / 發現 N 筆差異+內容節錄」(原生不輸出統計數字)。
- 升級方式: 覆蓋腳本檔即可，既有 conf 不用改 (未設 FULLCHECK_DIR 時行為與前版完全相同)。

部署四步驟
----------
1. 把 myship-monitor/ 整個上傳主機 (建議 /opt/starco/myship-monitor)，建立設定:
     cd /opt/starco/myship-monitor
     cp myship.conf.example myship.conf && chmod 600 myship.conf
   必改三項: LOG_FILE (實際 log 路徑)、SENDGRID_API_KEY (金鑰)、HOST_ROLE (測試機/正式機)
   ※ 執行檔若非 nimo-shake / nimo-shake.linux 命名，另需調整 PROC_PATTERN

2. 驗證讀得到 log (不寄信):
     head -c 100 /var/log/nimoshake/myship/nimo-shake.log   # Permission denied = 帳號沒讀取權，見下方【重要】
     bash nimoshake-monitor.sh                 # 不帶參數，自動用 myship.conf 的 LOG_FILE
     bash nimoshake-alert.sh --status myship.conf
   ※ 若 head 顯示 Permission denied (NimoShake 由 root 啟動時的正常現象)，
     上面的手動指令請一律加 sudo 執行 (sudo bash ...)，排程也必須裝 root (見步驟 3)。
     日常看即時狀態: sudo bash nimoshake-monitor.sh (不用帶參數)，
     啟動後畫面會自動持續刷新 (每 10 秒)，Ctrl-C 結束；要單次報表加 --human。

3. 裝排程: cd 到步驟 1 上傳的 myship-monitor 資料夾，先 ls 確認看得到 nimoshake-alert.sh 和 myship.conf，
   再執行 pwd，把印出來的路徑填進 crontab.example 的 BASE=，然後 sudo crontab -e 貼入。
   確認: 1 分鐘後 sudo cat state/alert.log 應有紀錄。
   【重要】排程一律用 sudo crontab -e 裝在 root 底下:
   NimoShake 由 root 啟動時 log 權限通常是 640，一般帳號讀不到，
   排程裝一般帳號會一直誤報 LOG_MISSING (實際部署已踩過此坑)；
   裝好後用 sudo crontab -l 確認內容存在。
   執行期狀態自動寫入程式資料夾內的 state/。
   (選用) 要讓非 root 帳號免 sudo 看現況，可啟用 crontab.example 內註解的報表排程。

4. 預設 DRY_RUN=1 只寫 state/alert.log 不寄信，觀察數日確認判斷正確後，
   把 myship.conf 的 DRY_RUN 改 0 正式啟用。

部署後自我檢查
--------------
- state/alert.log 的「首次執行，建立 log 基準點」只該出現一次且 offset 為實際檔案大小；
  若每分鐘重複出現且 offset=0 → LOG_FILE 讀不到 (路徑或權限問題)，
  排查步驟見 交付文件 3.4「常見部署問題排查」。
- state/alert.log 前綴判讀: INFO=純記錄 (無寄信動作)、OK=本輪無需寄信、
  DONE=本輪實際有寄信 (dry_run=1 時為彩排記錄，未真的寄)、WARN=警告需人工留意。
- sudo bash nimoshake-monitor.sh 應能看到完整報表並持續刷新 (Ctrl-C 結束；
  增量期看 [2] 的事件速率與同步延遲；全量期看 [3] 的進度%)。
  若有啟用選用報表排程，亦可 cat state/report.txt。

驗收演示 (選用)
---------------
bash demo-alert-flow.sh myship.conf          # dry-run 彩排
bash demo-alert-flow.sh --send myship.conf   # 真實寄信: 新增/持續/log遺失/解除 四封
(演示 log 來源用 DEMO_SOURCE_LOG=/path/to/real.log 指定；不會動正式 state)
