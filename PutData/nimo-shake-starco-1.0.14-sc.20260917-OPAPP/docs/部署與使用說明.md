# NimoShake-StarCo OPAPP 型別轉換專版 — 部署與使用說明

> 版本:nimo-shake-starco 1.0.14-sc.20260917-OPAPP(nimo-shake + nimo-full-check,2026-09-17 build)
> 轉型契約:contract-2026-09-11.1;規則檔 `type_rules_opapp.json`(config_id `opapp.type-conversion`、config_version `2026-09-11.1`)
> 驗證報告見 docs/驗證報告_2026-09-17.md。標示 `⬜ 待補（客戶環境）` 的值須在客戶環境實測後填入。

## 一、包內容

```
nimo-shake.linux              搬遷工具(DynamoDB→MongoDB,含 mchange_cast 型別轉換、啟動 preflight、checkpoint 規則指紋)
nimo-full-check.linux         校驗工具(逐欄位型別驗證、規則覆蓋完整性閘門;linux/amd64,動態連結)
nimo-shake.conf               搬遷設定檔(填 id / 憑證 / 連線字串後直接使用)
nimo-shake.conf.example       設定檔原始模板(改壞了可以 diff 回來)
type_rules_opapp.json         23 表 / 43 個受治理欄位轉型規則(兩工具共用同一份;scope.database 須改成 conf 的 id)
start.sh / stop.sh            啟停腳本(背景啟動 + preflight;安全停止)
SHA256SUMS                    檔案指紋(sha256sum -c SHA256SUMS)
docs/部署與使用說明.md        本文件
docs/驗證報告_2026-09-17.md   本機實驗室驗證報告 + 客戶環境補驗清單
```

## 二、前置需求

- Linux x86_64,具相容 glibc 的一般發行版(binary 為 Go 1.20.14 動態連結)
- 網路可達:來源 AWS DynamoDB(含 DynamoDB Streams,`sync_mode = all` 時需要)與目標 MongoDB
- AWS Access Key / Secret(DynamoDB 讀取權限;增量另需 Streams 讀取權限)
- MongoDB 帳號需具備**兩個庫**的 `readWrite` + `dbAdmin`:業務庫 `<id>` 與 checkpoint 庫 `<id>-checkpoint`
- 來源 23 張表若要走增量,每張表的 Stream 必須啟用

## 三、部署

```bash
tar -xzf nimo-shake-starco-1.0.14-sc.20260917-OPAPP.tar.gz
cd nimo-shake-starco-1.0.14-sc.20260917-OPAPP
sha256sum -c SHA256SUMS
chmod +x nimo-shake.linux nimo-full-check.linux start.sh stop.sh
./nimo-shake.linux -version && ./nimo-full-check.linux --version   # 兩者都應含 contract=contract-2026-09-11.1
```

## 四、設定

### 4.1 nimo-shake.conf 要動的鍵

| 鍵 | 出廠值 | 改成 |
|---|---|---|
| `id` | `REPLACE_WITH_TARGET_DATABASE_ID` | 目標資料庫名(⬜ 待補（客戶環境）)。**同時決定** 目標 db 名、checkpoint 庫名 `<id>-checkpoint`、pid 檔名 `<id>.pid` |
| `sync_mode` | `all` | 全量 + 增量(程序不會自行退出);只做全量改 `full`(跑完自行退出)|
| `source.access_key_id` / `source.secret_access_key` | `REPLACE_WITH_AWS_ACCESS_KEY_ID` / `REPLACE_WITH_AWS_SECRET_ACCESS_KEY` | 實際金鑰 |
| `source.region` | `REPLACE_WITH_AWS_REGION` | 來源區域(⬜ 待補（客戶環境）)|
| `source.endpoint_url` | 空 | **留空**(走真 AWS;設了 endpoint 產品只允許 `sync_mode = full`)|
| `target.address` | `REPLACE_WITH_MONGODB_URI` | 實際 MongoDB 連線字串 |
| `filter.collection.white` | 23 張表(分號分隔)| 不動。白名單必須與規則檔宣告的 23 表完全相同 |

不動但必須知道的鍵:

| 鍵 | 值 | 意義 |
|---|---|---|
| `convert.type` | `mchange_cast` | 啟用型別轉換(不是 `mchange`)|
| `convert.type_rules_path` | `./type_rules_opapp.json` | 規則檔相對路徑;路徑錯直接啟動失敗(fail-fast)|
| `convert._id` | `pre` | 來源 23 表都沒有 `_id` 欄位,此鍵實際無作用,但校驗端 `--convertId` 須與它一致 |
| `target.db.exist` | `drop` | **走全量路徑時先逐 collection 清空目的端再搬** |
| `target.mongodb.type` | `replica` | 目標為複本集 |
| `checkpoint.type` / `checkpoint.db` | `mongodb` / 空 | checkpoint 存目的端 MongoDB,庫名預設 `<id>-checkpoint`。⚠️ 若改用 `file`,落檔目錄取 **`checkpoint.db`** 的值,`checkpoint.address` 被忽略 |
| `log.file` | `nimo-shake.log` | 相對路徑,落在啟動當時的工作目錄 |
| `full_sync.http_port` / `incr_sync.http_port` | `9341` / `9340` | 全量進度 / 增量 metric 端點 |

⚠️ 確認 conf 內**沒有**未註解的 `full.read.filter_expression` / `full.read.filter_attributevalues`(本包出廠已移除;若從舊包複製 conf 過來要檢查)。有這兩行時 DynamoDB 會掃完全部資料再過濾,症狀是「跑很久、進度一直動,但目的端 0 筆」,而且 `drop` 已先執行。

### 4.2 type_rules_opapp.json 要動的鍵

只改一個:`scope.database`(出廠值 `REPLACE_WITH_SAME_TARGET_DATABASE_ID`,與 conf 的佔位**刻意不同**)→ 改成與 conf 的 `id` 相同的實際資料庫名。兩邊沒一起改,啟動即失敗。其他內容(23 表、43 條規則)不得修改;改了 SHA256 就與 `SHA256SUMS`、啟動摘要不符(改 `scope.database` 本身也會改變 SHA256,啟動摘要的 `rules_sha256` 以改完後的檔案為準)。

### 4.3 啟動前一次確認

```bash
grep -nE "^(id|sync_mode|source\.(region|endpoint_url)|target\.(address|db\.exist|mongodb\.type)|convert\.(type|type_rules_path|_id)|filter\.collection|checkpoint\.(type|db)|full\.read\.filter)" nimo-shake.conf
grep -o '"database"[^,]*' type_rules_opapp.json
pgrep -af nimo-shake        # 應無輸出
```

## 五、執行搬遷(nimo-shake)

### 5.1 啟動

```bash
./start.sh                                   # 背景啟動 + preflight(binary / conf / 規則檔 / 重複啟動);預設 nimo-shake.conf
# 或手動:
setsid nohup ./nimo-shake.linux -conf ./nimo-shake.conf > ns_run_$(date +%m%d).log 2>&1 &
tail -f nimo-shake.log
```

兩個 log 都要保留:`nimo-shake.log`(程式 log:進度、啟動摘要、轉型例外)與 stdout 導出檔(抓 panic / 啟動即失敗原因)。
⚠️ 交付包沒有自動重啟機制(前版 hypervisor 已移除):「重啟迴圈 + `drop`」會反覆清空目的端。如需常駐監管請用 systemd `Restart=on-failure`。

### 5.2 啟動摘要三行(每個程序只印一次,缺一行即異常)

```text
schema=v2 semantics=collection_scoped config_id=opapp.type-conversion config_version=2026-09-11.1 database=<conf 的 id> collections=23 governed_collections=20 preserve_only=3 rules=43 rules_sha256=<規則檔 SHA256>
source _id fields=0; convert._id has no effect
source_id_basis=declared_mapping convert_id=pre
```

| 看哪裡 | 應為 | 不符代表 |
|---|---|---|
| `schema=` | `v2` | 印出 `schema=v1 ... scope_database=unbound` → 裝到前版(v1)規則檔,立即停止 |
| `database=` | 等於 conf 的 `id` | 規則檔不是給這個庫的(程式會在此之前拒絕啟動)|
| `collections=23 governed_collections=20 preserve_only=3 rules=43` | 字面完全相同 | 規則檔被改過或不完整 |
| `rules_sha256=` | 等於現場 `sha256sum type_rules_opapp.json`(填完 `scope.database` 後的檔案);記下這個值,校驗工具與 checkpoint 指紋都要對上 | 規則檔不是現場那份(`SHA256SUMS` 只驗出廠檔,填值後 hash 必然不同)|

摘要之後應依序出現 `prepare checkpoint done` → `start full sync` → `finish fetching table list: [23 張表]` → `target.db.exist is set[drop]` → `start syncing` → `New session to mongodb+srv://<帳號>:***@... successfully`。

### 5.3 啟動 preflight 拒絕(目的端與 checkpoint 零異動)

摘要與 `start full sync` 之間若出現以下錯誤,程式直接停止,修 conf 或規則檔後重啟即可,不需處理目的端:

| 情況 | log 字面(節錄)|
|---|---|
| 規則檔 `scope.database` ≠ conf `id` | database 不符的錯誤 |
| 白名單少一張 | `selected collections do not match contract: missing=[<表名>] extra=[]` |
| 白名單多一張(規則檔未宣告)| `selected collections do not match contract: missing=[] extra=[<表名>]` |
| 白名單拼錯 | `selected collections do not match contract: missing=[<正確表名>] extra=[<拼錯表名>]` |
| 規則欄位撞到該表 Partition Key / Sort Key | key collision 錯誤 |

白名單與黑名單**都留空 = 全部同步**:此時拿來源端實際解析出的表清單比對規則檔的 23 表,同樣受上表保護。

### 5.4 全量完成與接上增量

```bash
grep -n "full sync done" nimo-shake.log                 # 全量完成
mongosh "<MONGO_URI>" --quiet --eval 'const d = db.getSiblingDB("<id>"); d.getCollectionNames().sort().forEach(c => print(c, d[c].countDocuments({})))'
curl -s http://127.0.0.1:9340/metric                    # 增量 metric(sync_mode=all;全量期間連不上是正常的)
```

- `sync_mode = full`:`full sync done!` → `sync complete!` 後程序自行退出
- `sync_mode = all`:`full sync done!` 後轉入增量,`records_get` 與 `records_write` 相等即無積壓;計數器是行程內累計,重啟歸零屬正常
- ⚠️ 不要用 DynamoDB `ItemCount` 對帳(約每 6 小時更新的估計值);以校驗工具的 `checked` 為準
- 全量耗時、筆數:⬜ 待補（客戶環境）(本機實驗室 1,380 筆合成資料 72 秒,不可用來推估)

### 5.5 停止與重啟續跑

**停止**(pid 檔名為 `<id>.pid`,先驗身分再 kill):

```bash
./stop.sh
# 或手動:
ps -p "$(cat <id>.pid)" -o pid,cmd        # 指令內容必須是 nimo-shake.linux
kill -TERM "$(cat <id>.pid)"
pgrep -af nimo-shake                       # 應查無結果
```

程序還在跑時再啟動一次,會被 pid 鎖擋下(`write pid failed. Locked by other process`),只印在終端不寫 log;pid 檔寫在啟動當時的工作目錄,務必在同一目錄操作。

**重啟前五條檢核(全過才可重啟)**:

| ☐ | 檢核 | 怎麼查 | 不成立的後果 |
|---|---|---|---|
| ☐ | checkpoint 狀態為 `incr_sync` | `mongosh "<MONGO_URI>" --quiet --eval 'printjson(db.getSiblingDB("<id>-checkpoint").status_table.find({Key:"status_key"}).toArray())'` | 重跑全量 → `drop` |
| ☐ | 距程序停止未超過 24 小時 | `ls -l --time-style=full-iso nimo-shake.log; date` | Stream 位置已淘汰,重跑全量(狀態值**不會**變)|
| ☐ | 來源端表清單與啟動時相同 | log 最後一行 `finish fetching table list` 對 `aws dynamodb list-tables` | 重跑全量(狀態值不會變;同帳號下多一張任何表都算)|
| ☐ | 23 張表 Stream 皆仍啟用 | `aws dynamodb describe-table --table-name <表> --query 'Table.StreamSpecification'` | 重跑全量(狀態值不會變)|
| ☐ | 規則檔 SHA256 / `config_version` / `convert.type` / `convert._id` / `database` 與 checkpoint 的 `Fingerprint` 相同 | 同第一條,看 status 文件的 `Fingerprint` 欄 | **啟動即 error 退出**(不續跑、不重跑、不 drop),須二選一處置 |

status 文件形狀(欄位以 file 模式實收;mongodb 模式欄位相同為假設,客戶環境核對):

```json
{"Key":"status_key","StatusValue":"incr_sync","Fingerprint":{"ckpt_schema":"ns-ckpt-2026-09-11.1","schema_version":2,"config_id":"opapp.type-conversion","config_version":"2026-09-11.1","rules_sha256":"<規則檔 SHA256>","convert_type":"mchange_cast","convert_id":"pre","database":"<id>"}}
```

指紋不符時的處置:**A.** 把規則檔 / conf 還原成 checkpoint 記錄的那一版再重啟;或 **B.** 清空 `<id>-checkpoint` 庫 → 重新啟動(走全量並 `drop`)→ 全量完成後重跑第六節校驗。⛔ 禁止手動改 `StatusValue` 或塞指紋欄位繞過。

⚠️ 指紋核對**只保護「從 `incr_sync` 續跑」**。改了規則檔後直接以 `full` 重跑、或 checkpoint 不是 `incr_sync`,**不會被擋**,會依 `target.db.exist = drop` 重建全部 collection。要不要重建由 `sync_mode` 與 `target.db.exist` 決定,指紋不會替你擋。

**前四條任一不成立 → 不要重啟**。先確認 MongoDB 備份與還原程序,評估重跑全量期間目的端為空的影響,業務端同意後才依 5.1 重啟。不要用「先啟動看看,看到 drop 再 Ctrl+C」試探,`drop` 是全量路徑第一個動作。

重啟後判定「真的接上了、沒有重搬」:啟動摘要三行 → `end check checkpoint` → **直接接 `start incr sync`**,中間沒有 `start full sync`、沒有 `target.db.exist is set[drop]`。`isn't exist on the stream, status[no need to process]` 的 WARN 與計數器歸零都是假警報。
此段畫面本機實驗室無法取得:⬜ 待補（客戶環境）。

## 六、資料校驗(nimo-full-check)

### 6.1 執行腳本

金鑰直接從 `nimo-shake.conf` 讀,避免兩邊不一致。

```bash
cat > run-fullcheck.sh <<'EOS'
#!/bin/bash
CONF=./nimo-shake.conf
AK=$(grep -E '^\s*source\.access_key_id'     $CONF | cut -d= -f2- | xargs)
SK=$(grep -E '^\s*source\.secret_access_key' $CONF | cut -d= -f2- | xargs)
TGT=$(grep -E '^\s*target\.address'          $CONF | cut -d= -f2- | xargs)
OUT=out_check_$(date +%m%d)

./nimo-full-check.linux \
  -s "$AK" --sourceSecretAccessKey="$SK" \
  --sourceRegion=<region> \
  -t "$TGT" \
  -i <id> \
  -c mchange_cast --convertTypeRulesPath=./type_rules_opapp.json \
  --convertId=pre \
  -m dynamodb --sample=0 \
  --filterCollectionWhite="cmn_activity_m;cmn_coupon_m;ec_qrcode_benefits_code;ec_qrcode_benefits_codemapping;ec_qrcode_benefits_main;egtc_traded_m;event_record_main;event_record_traded_m;external_import_traded_m;imm_traded_m;inapp_notice_m;inside_link_m;itc_coupon_m;member_benefits_m;mms_coupon_m;mms_event_record;my_notice_m;pos_activity_m;pos_coupon_m;s_feature;s_vender_business_config;user_account_m;user_def_payment" \
  --scanSegments=8 \
  --checkpointFile=${OUT}.ckpt.json \
  --convergeRetries=2 --convergeDelayMs=5000 \
  -d $OUT

echo "exit=$?" > ${OUT}.exitcode
EOS
chmod +x run-fullcheck.sh
setsid nohup ./run-fullcheck.sh > fullcheck-$(date +%Y%m%d).log 2>&1 &
sleep 10; pgrep -af nimo-full-check          # 必須恰好一行;多行 = 重複啟動,checkpoint 會互相覆蓋
```

`<region>`、`<id>`:⬜ 待補（客戶環境）。校驗耗時:⬜ 待補（客戶環境）(與資料量成正比,必須背景執行)。

### 6.2 參數說明

| 參數 | 值 | 意義 |
|---|---|---|
| `--sample=0` | `0` | **0 = 全量逐筆**。預設值是 1000,不寫就只比每表 1000 筆 |
| `--convertId=pre` | `pre` | 必須與 conf 的 `convert._id` 一致 |
| `-c` / `--convertTypeRulesPath` | `mchange_cast` / 規則檔 | 校驗端用同一套規則計算期望值;啟動時印同格式的啟動摘要 |
| `--filterCollectionWhite` | 23 張表 | 必須列全(含 3 張 preserve-only)。少一張、拼錯、多列一張 DynamoDB 存在但規則檔未宣告的表 → 啟動即 `EXECUTION_ERROR`(exit 2)。多寫一個 DynamoDB **不存在**的表名不擋(仍涵蓋宣告的 23 表)|
| `--scanSegments=8` | `8` | 分段平行掃描;效益須在客戶環境實測 |
| `--checkpointFile` | `<OUT>.ckpt.json` | 中斷後可 `--resume` 續跑。⚠️ 任何 resume 結果都標 `coverage_complete=false`,**不作完整性證明**;完整驗收須不帶 resume 全量重跑 |
| `--convergeRetries` / `--convergeDelayMs` | `2` / `5000` | 增量仍在跑時對疑似不符重抓確認,避免時間差誤報(`TRANSIENT_CONVERGED`,資訊性)|
| `-m both` | 選用 | 反向檢查目標端多出的資料(`TARGET_ONLY`);不支援分段與 checkpoint |

### 6.3 報告判讀

**第一步看 exit code**:

| exit | `outcome` | 觸發條件 | 該怎麼辦 |
|---|---|---|---|
| **0** | `PASS` | 全部通過,且規則覆蓋完整 | ✅ 完成 |
| **1** | `FAIL` | `failed > 0` 或 `target_only > 0` | 🔴 資料不符,看 `out_check_*/<表名>` 的 diff 行(主鍵 / 欄位路徑 / 兩端值 / 分類 / reason)|
| **2** | `EXECUTION_ERROR` | `execution_errors > 0` 或 `skipped > 0`,**或規則覆蓋閘門未過**(任一受治理規則 `zero_hits`、resume 續跑、原 PASS 但某規則沒有可轉型的觀察值)| ⚠️ 沒跑完或證據不完整,`checked` 不可對帳;排除後**不帶 resume 全量重跑** |
| **3** | `PASS_WITH_EXCEPTIONS` | 只有 `exceptions > 0`(`SOURCE_UNCASTABLE`)| ⚠️ **不是全綠**。OPAPP 預期會有:5 張 N/S 表的 seqno 前導零 / `-0` / 非數字字串被正確拒轉保留。每筆例外附 `reason`、來源值、主鍵,由專案負責人逐案判定 |

結案條件:exit 0;或 exit 3 + 例外清單 + 逐案判定紀錄。

診斷分類:`CAST_MISSED`(該轉沒轉)/ `CAST_WRONG_VALUE`(轉了值錯)/ `TYPE_UNEXPECTED`(意外型別,含被拒轉的 `"007"` 在目的端變成 `"7"`)/ `SOURCE_UNCASTABLE`(來源不可轉,計入 exceptions)/ `DATA_DIFF`(非受治理欄位差異)/ `TARGET_ONLY`(目標端多出)/ `TRANSIENT_CONVERGED`(暫態已收斂,資訊性)。
`SOURCE_UNCASTABLE` 的 `reason`:`LEADING_ZERO`、`NEGATIVE_ZERO`、`INVALID_INTEGER`、`FRACTIONAL`、`OUT_OF_RANGE`、`TYPE_MISMATCH`。

**第二步確認是全量**(`run-manifest.json`,四欄缺一不可):

```bash
grep -oE '"sample":[0-9]+|"segment_sampled":[a-z]+|"segment_coverage":[0-9.]+|"filter_collection_white":"[^"]*"' out_check_*/run-manifest.json
```

`parameters.sample` = **0**、`segment_sampled` = `false`、`segment_coverage` = `1`、`filter_collection_white` = 23 張表。`segment_*` 兩欄擋不住 `--sample=1000` 的抽樣,一定要看第一欄。`skipped` 與 `execution_errors` 皆須為 0。

**第三步看 `rule-coverage.json`**(回答「規則到底有沒有套用到」):

| header 欄位 | 應為 |
|---|---|
| `schema_version` / `semantics` | `2` / `collection_scoped` |
| `config_id` / `config_version` | `opapp.type-conversion` / `2026-09-11.1` |
| `database` / `rules_sha256` | conf 的 `id` / 與搬遷工具啟動摘要、現場 `sha256sum type_rules_opapp.json` 相同 |
| `rules_declared` / `rules_expected` / `rules_registered` | `43 / 43 / 43`,`rules` 陣列恰 43 列 |
| `collections_selected` / `preserve_only_collections` | 23 張 / 3 張(`ec_qrcode_benefits_codemapping`、`user_def_payment`、`s_feature`)|
| `sampled` / `coverage_direction` | `false` / `forward`(或 `both`)|
| **`coverage_complete`** / `coverage_notes` | **`true`** / `[]`(可能出現:`zero_hits:<表>:<欄>`、`no_convertible_observation`、`sampled`、`resume_partial_observations`)|

43 列逐列:`cast_missed` / `cast_wrong_value` / `type_unexpected` 皆為 0;`source_uncastable` 只在 5 個 seqno 列允許 > 0,且逐筆在例外清單有 `reason`;`suspicious` 為 `[]`。
`cast_missed = 0` 是必要條件不是充分條件——規則沒碰到資料時它也是 0,所以 header 的 43 列與 `coverage_complete = true` 一定要同時確認。**不以「log 沒有 WARN」作任何判定。**

`run-manifest.json` 自動遮罩連線密碼(`REDACTED`),可直接提供第三方查驗;但 diff 檔的 `DATA_DIFF` 會印兩端原值,分享前注意。

## 七、改規則後的重跑

規則檔在啟動時載入,**改規則不會回溯既有資料**。要讓既有資料套用新規則必須重跑全量(會觸發 `drop`),完成後重跑第六節校驗。只影響往後增量時,依 5.5 的指紋處置(選項 B 清 checkpoint 後全量);直接以 `full` 重跑不會被指紋擋,但同樣是一次完整重建。

## 八、建議導入步驟

1. 以小樣本試跑(確認憑證、連線、啟動摘要三行、preflight、報告產出)
2. 逐步放大,觀察 `qps.full` / `--qpsFull` / `--qpsMongo` 對兩端負載;記錄全量耗時填入 ⬜ 待補（客戶環境）
3. 正式全量 → 全量校驗(不帶 resume,取得 `coverage_complete = true`)→ exit 0 或 exit 3 + 逐案判定
4. 接上增量後,依驗證報告的「客戶環境補驗清單」逐項補驗(增量、續跑、指紋拒絕)
