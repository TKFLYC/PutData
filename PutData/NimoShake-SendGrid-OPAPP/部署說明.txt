本版更新 (v4.3)
-------------
- Table 進度直接採 NimoShake 即時統計: 程序在跑時，報表 [3] 的已搬筆數/總筆數/進度%/預計剩餘
  直接取自 NimoShake 內建 API (localhost:9341/progress)，不用設 TABLE_TOTALS、不用設任何東西。
  09/03 畫面上 [3] 顯示 "-" 是舊版只認 conf 基準、沒去讀 API；升級後同畫面會顯示 1.74%、612175/35109579。
  API 打不到 (程序沒跑、離線看歷史 log) 才退回 log 估算 + conf TABLE_TOTALS。
- CDC (增量) 讀取/寫入操作資訊: 報表 [2] 與告警信判讀表新增「CDC 讀寫」列，三個來源疊加——
  (1) NimoShake 增量 API 9340/metric 的累計讀取/寫入/待寫/checkpoint 次數；
  (2) log 取樣的 INSERT/MODIFY/REMOVE 批數與筆數、讀取重試次數；
  (3) 專版每 5 秒一行的統計行 [stage=incr, get=N, write_success=N, tps=N, ckpt_times=N]:
      顯示最新一行的 讀取 get / 寫入 write_success / 待寫 / tps / checkpoint，以及取樣區間內讀了寫了多少。
  純資訊列，不新增告警條件。
  注意: 實際 log 字樣是 stage=incr (等號)，手動 grep 請用 grep "stage=incr"；用 stage-incr 會抓不到。
- 中斷/續傳/追趕判讀 (常駐畫面 [2] 與告警信): 顯示「本檔啟動 N 次，最近 HH:MM → 從 checkpoint 續傳增量 / 重跑全量」；
  資料延遲加狀態標籤 [追平/追趕中/閒置/落後/中斷]；斷線時直接印「已中斷 X，資料停在 HH:MM:SS(來源時間)，距今 Y」，
  重啟接續後印「追趕中: 延遲由 A 縮到 B」。程序死掉 API 消失時，[3] 已搬/總數/進度% 與 CDC 累計改顯示
  中斷前最後值 (state/.api_snapshot 快照) 並加註「還差 N 筆」，不再變成 "-"。
- 修正: 舊版「同步延遲」永遠顯示 0 秒 (拿 checkpoint 寫入時間比行時間，兩者都是當下)。
  新版改用來源事件時間 (DynamoDB Stream 的 ApproximateCreationDateTime)，顯示的是真實資料延遲。
  來源沒新資料時延遲會自然變大，畫面會標 [閒置] 不算異常；有在寫但延遲超過 STALL_SECONDS 才標 [落後] 異常。
- conf 新增選填參數 (見 opapp.conf.example): HTTP_FULL_PORT / HTTP_INCR_PORT (API 端口不是預設時才設)、INCR_TAG (預設 stage=incr)。
- 升級方式: 覆蓋 opapp-monitor 資料夾內的 nimoshake-monitor.sh、nimoshake-alert.sh 即可，既有 conf 不用改。
前版更新 (v4.2；09/01 文件補充，程式不變)
-------------
- (09/01) 補充「看門狗驗證」與「告警頻率說明」兩節 (見本檔下方)；
  交付文件同步新增 2.1.2 嚴重度分級定義、2.1.3 提醒頻率 (REALERT_INTERVAL) 說明、
  2.7.1 看門狗設定與驗證步驟。
- 新增「FullCheck 結束通知」: 在 conf 加一行 FULLCHECK_DIR (nimo-full-check.linux 的執行目錄) 後，
  nimo-full-check 全量複核照原本指令跑完 (輸出資料夾出現 run-manifest.json) 1 分鐘內自動寄結果信:
  🟢 PASS / 🟠 PASS_WITH_EXCEPTIONS / 🔴 FAIL + 各 table 統計 (checked/passed/failed/exceptions) +
  異常欄位 Top 5 + 耗時。同一次結果只通知一次 (重跑後舊輸出資料夾被改名加時間戳也不會誤寄)；
  首次啟用只建基準、不補寄歷史結果。範例見 opapp.conf.example 的 FULLCHECK_DIR 區塊。
- FullCheck 失敗也會通知: 同時追蹤 fullcheck 程序，程序消失卻沒有新結果檔
  (OOM/kill/連線中斷/磁碟滿) → 寄 🔴「FullCheck 異常結束」告警，附排查步驟；
  判斷前保留約 1 分鐘寬限，避免程序剛結束、結果檔還在寫的誤報。
- 新增「看門狗」(nimoshake-watchdog.sh): 監控「告警引擎本身」——引擎每輪跑完寫心跳，
  看門狗每 5 分鐘獨立檢查，心跳停更 5 分鐘即寄 🔴「監控引擎停擺 (告警失效中)」、
  恢復寄 🟢。看門狗完全不共用引擎程式碼，引擎壞掉仍能寄信。
  排程行已加入 crontab.example，照步驟 3 貼入即自動生效。
- 原生版 fullcheck (不寫 run-manifest.json 的 git 版) 也支援: conf 設
  FULLCHECK_MODE="native"、FULLCHECK_DIR 直接填 -d 輸出資料夾本身，
  並建議設 FULLCHECK_NATIVE_LOG=<啟動時導出的log檔> 以區分跑完/中途掛掉。
  原生版信件為「未發現差異 / 發現 N 筆差異+內容節錄」(原生不輸出統計數字)。
- 升級方式: 覆蓋腳本檔即可，既有 conf 不用改 (未設 FULLCHECK_DIR 時行為與前版完全相同)。

部署四步驟
----------
1. 把 opapp-monitor/ 整個上傳主機 (建議 /opt/starco/opapp-monitor)，建立設定:
     cd /opt/starco/opapp-monitor
     cp opapp.conf.example opapp.conf && chmod 600 opapp.conf
   必改三項: LOG_FILE (實際 log 路徑)、SENDGRID_API_KEY (金鑰)、HOST_ROLE (測試機/正式機)
   ※ 執行檔若非 nimo-shake / nimo-shake.linux 命名，另需調整 PROC_PATTERN

2. 驗證讀得到 log (不寄信):
     head -c 100 /var/log/nimoshake/opapp/nimo-shake.log   # Permission denied = 帳號沒讀取權，見下方【重要】
     bash nimoshake-monitor.sh                 # 不帶參數，自動用 opapp.conf 的 LOG_FILE
     bash nimoshake-alert.sh --status opapp.conf
   ※ 若 head 顯示 Permission denied (NimoShake 由 root 啟動時的正常現象)，
     上面的手動指令請一律加 sudo 執行 (sudo bash ...)，排程也必須裝 root (見步驟 3)。
     日常看即時狀態: sudo bash nimoshake-monitor.sh (不用帶參數)，
     啟動後畫面會自動持續刷新 (每 10 秒)，Ctrl-C 結束；要單次報表加 --human。

3. 裝排程: cd 到步驟 1 上傳的 opapp-monitor 資料夾，先 ls 確認看得到 nimoshake-alert.sh 和 opapp.conf，
   再執行 pwd，把印出來的路徑填進 crontab.example 的 BASE=，然後 sudo crontab -e 貼入。
   確認: 1 分鐘後 sudo cat state/alert.log 應有紀錄。
   【重要】排程一律用 sudo crontab -e 裝在 root 底下:
   NimoShake 由 root 啟動時 log 權限通常是 640，一般帳號讀不到，
   排程裝一般帳號會一直誤報 LOG_MISSING (實際部署已踩過此坑)；
   裝好後用 sudo crontab -l 確認內容存在。
   執行期狀態自動寫入程式資料夾內的 state/。
   (選用) 要讓非 root 帳號免 sudo 看現況，可啟用 crontab.example 內註解的報表排程。

4. 預設 DRY_RUN=1 只寫 state/alert.log 不寄信，觀察數日確認判斷正確後，
   把 opapp.conf 的 DRY_RUN 改 0 正式啟用。

看門狗驗證 (建議上線前做一次)
-----------------------------
看門狗 (nimoshake-watchdog.sh) 負責「告警引擎自己壞掉」時發信。設定不需額外動作:
排程行已在 crontab.example (*/5 那行)，照步驟 3 貼入即生效，conf 不需加任何參數。
驗證三步:
1. sudo crontab -l 應看到 nimoshake-watchdog.sh 那行 (每 5 分鐘)。
2. 手動跑一次: sudo bash nimoshake-watchdog.sh opapp.conf
   —— 心跳正常時「靜默結束、無輸出」是正常的 (state/watchdog.log 平時是空的)。
3. 實測會發信: 暫時把 crontab 裡「告警引擎」那行註解掉 (保留看門狗行)，
   5-10 分鐘內應收到 🔴「監控引擎停擺 (告警失效中)」；
   取消註解恢復後，5 分鐘內會再收到 🟢「監控引擎已恢復」。
注意: 看門狗同樣尊重 DRY_RUN —— conf 是 DRY_RUN=1 時只記 watchdog.log 不真寄，
實測前 conf 需已改 DRY_RUN=0。上線時 DRY_RUN 改 0 一次，引擎與看門狗一起生效。

告警頻率說明 (為什麼第一封之後沒再寄?)
--------------------------------------
設計是「同一問題只通知一次、不重複轟炸」: 問題新增時寄 🔴 一封，之後持續存在
預設每 6 小時 (REALERT_INTERVAL=21600) 才寄一封 🟠 提醒，解除時寄 🟢 一封。
中間每分鐘的檢查都只在 state/alert.log 記一行「OK: 本次無需寄信」——這是正常的，
不是排程卡住。確認沒卡住的方法:
  sudo tail -20 state/alert.log    # 每分鐘應有一行
  sudo cat state/.heartbeat        # 心跳時間戳應在 1 分鐘內
另注意: 若第一封是用 --send 手動寄的、而排程 conf 仍是 DRY_RUN=1，
也會呈現「第一封有、之後都沒有」，查 alert.log 有無「DRY_RUN: 略過寄信」即可分辨。
想提醒更頻繁: conf 的 REALERT_INTERVAL 調小 (例 3600=每小時；0=不重複提醒)。
嚴重度分級: high/medium 會寄信，low (慢讀寫) 預設只記錄不寄
(ALERT_MIN_SEVERITY=medium，要收 low 改設 low)。詳見交付文件 2.1.2 / 2.1.3。

部署後自我檢查
--------------
- state/alert.log 的「首次執行，建立 log 基準點」只該出現一次且 offset 為實際檔案大小；
  若每分鐘重複出現且 offset=0 → LOG_FILE 讀不到 (路徑或權限問題)，
  排查步驟見 交付文件 3.4「常見部署問題排查」。
- state/alert.log 前綴判讀: INFO=純記錄 (無寄信動作)、OK=本輪無需寄信、
  DONE=本輪實際有寄信 (dry_run=1 時為彩排記錄，未真的寄)、WARN=警告需人工留意。
- sudo bash nimoshake-monitor.sh 應能看到完整報表並持續刷新 (Ctrl-C 結束；
  增量期看 [2] 的事件速率與同步延遲；全量期看 [3] 的進度%)。
  若有啟用選用報表排程，亦可 cat state/report.txt。

驗收演示 (選用)
---------------
bash demo-alert-flow.sh opapp.conf          # dry-run 彩排
bash demo-alert-flow.sh --send opapp.conf   # 真實寄信: 新增/持續/log遺失/解除 四封
(演示 log 來源用 DEMO_SOURCE_LOG=/path/to/real.log 指定；不會動正式 state)
